Process Studio Backend & Deploy

Documentacao completa da infraestrutura server-side do Process Studio: API backend (NestJS), banco de dados (PostgreSQL/Prisma), deploy em Docker Swarm com HTTPS automatico via Traefik, e pipeline CI/CD com GitHub Actions.

O backend do Process Studio e responsavel por autenticacao de usuarios, sincronizacao de dados entre dispositivos, distribuicao de atualizacoes do app desktop, e coleta de metricas de uso. O app desktop funciona 100% local mesmo sem conexao com o backend - a API e complementar, nao essencial.

4Autenticacao #

App (login)
→
POST /auth/login
→
JWT (15min) + Refresh (30d)
→
Device tracking
  • JWT Access Token: expira em 15 minutos (configuravel via JWT_EXPIRATION)
  • Refresh Token: expira em 30 dias (configuravel via JWT_REFRESH_EXPIRATION)
  • Refresh Token Rotation: a cada refresh, o token antigo e revogado e um novo e emitido
  • Device tracking: cada sessao e vinculada a um deviceId unico
  • Senha: hash com bcrypt (salt rounds configuravel)
  • Rate limiting: guard ativo em todos os endpoints de auth
  • Activity logging: toda acao de auth (login, logout, refresh, falha) e registrada com IP e user agent

6.2Migrations #

Migrations sao gerenciadas pelo Prisma e aplicadas automaticamente no startup do container:

BASH
# Desenvolvimento - criar nova migration
npx prisma migrate dev --name descricao_da_mudanca

# Producao - aplicar migrations pendentes (roda no entrypoint do Docker)
npx prisma migrate deploy

# Gerar client apos mudanca no schema
npx prisma generate
!

O container roda prisma migrate deploy antes de iniciar a aplicacao. Migrations destrutivas (drop column, drop table) devem ser feitas em duas etapas: primeiro remover o uso no codigo, depois a migration.

9CI/CD Pipeline #

Pipeline automatizado via GitHub Actions. Trigger: push na branch main.

Push main
→
Test
→
Build Image
→
Push Registry
→
Deploy (Portainer)
→
Health Check

Stage 1: Test

  • Ubuntu latest + Node.js 20
  • npm ci + npx prisma generate
  • npx tsc --noEmit - type checking
  • npm run lint - linting
  • npx jest --maxWorkers=2 --forceExit - testes unitarios

Stage 2: Build & Push

  • Docker BuildX com cache de camadas
  • Push para registry.digital-ai.tech/process-studio-api
  • Tags: :latest + :{SHORT_SHA}

Stage 3: Deploy

  • Deploy via Portainer API (nunca CLI)
  • Atualiza imagem para tag :{SHORT_SHA} (nao :latest)
  • Bump de ForceUpdate para recriar task
  • Monitora convergencia (uptime < 120s)
  • Poll no health check por ate 180s
  • Verifica se nao houve rollback automatico

Notificacoes

Cada etapa envia notificacao para o Discord via webhook n8n:

  • Pipeline iniciado
  • Build de imagem (sucesso / falha)
  • Deploy em andamento
  • Deploy concluido / falhou

11Health Check #

Endpoint: GET /health (publico, sem auth)

JSON - RESPOSTA
{
  "status": "ok",           // "ok" ou "degraded"
  "version": "0.4.25",
  "database": "connected",  // "connected" ou "disconnected"
  "uptime": 86400           // segundos
}

O Docker Swarm verifica o health a cada 30 segundos com timeout de 10s e 3 retries. Falha no health trigger rollback automatico.

12Sistema de Auto-Update #

App Desktop
→
GET /updates/tauri/:target/:arch/:ver
→
Versao nova?
→
Download via API (proxy GitHub)
→
Instala automaticamente
  • O app verifica updates periodicamente usando o Tauri v2 updater nativo
  • A API funciona como proxy para o GitHub Releases (repo privado)
  • O download e servido via /updates/download/:ver/:file usando o GITHUB_TOKEN do servidor
  • Admins publicam novas versoes via POST /updates/admin/versions
  • Cada check de update e registrado na tabela update_checks para analytics

Fluxo de Release

PASSOS
1. Build no Windows:  node release.cjs
   - Compila sidecar (.exe via pkg)
   - Compila app (Tauri + NSIS installer)
   - Publica no GitHub Releases

2. Registrar na API:  POST /updates/admin/versions
   - version, target, arch, download_url, signature, release_notes

3. App detecta:  GET /updates/tauri/windows/x86_64/0.4.24
   - Retorna JSON com url + signature da nova versao

4. Download + instalacao automatica pelo updater Tauri

13Metricas e Telemetria #

O app envia eventos de telemetria via POST /sync/batch com entityType: "metric". Admins consultam via:

HTTP
# Metricas paginadas com filtros
GET /admin/metrics?userId=abc&eventType=compile&from=2026-01-01&to=2026-12-31&page=1&limit=100

# Resumo estatistico
GET /admin/metrics/summary?from=2026-01-01&to=2026-12-31

Alem de metricas, a tabela activity_logs registra automaticamente:

  • login - usuario logou (IP, user agent, device)
  • logout - usuario deslogou
  • login_failed - tentativa de login falhou
  • app_opened - app foi aberto
  • refresh - token foi renovado
