O Desafio

Por que processar 108 mil artigos?

A base HELP do Bradesco é um dos maiores ativos de conhecimento da organização. Está presa em formato legado do SharePoint, sem inventário, sem qualidade medida e com duplicação desconhecida.

📄

Markup Pesado

HTMLs com classes MS-*, estilos inline, tabelas aninhadas e formatação legada do SharePoint. Impossível extrair conteúdo útil diretamente.

🔁

Duplicação Desconhecida

Sem inventário centralizado, não se sabe quantos artigos são duplicatas exatas ou semânticas entre as 26 áreas operacionais.

🏷

Classificação Rudimentar

Os TXTs trazem classificação por heurística simples (TEXTUAL, LINK_ONLY, SHORT_TEXT). Precisa de validação e refinamento com IA.

📊

Sem Quality Score

Nenhum artigo tem avaliação de completude, clareza ou atualidade. Impossível priorizar revisão humana sem uma métrica objetiva.

💥

Volume Inviável

108 mil artigos são inviáveis para revisão humana direta. Triagem automatizada com IA é pré-requisito para qualquer ação.

Pipelines

2 Pipelines de Processamento

Dois pipelines LLM complementares. A ingestão de arquivos e a deduplicação por hash e embeddings são processos separados, fora dos pipelines LLM.

Nota: A ingestão (leitura do filesystem e limpeza HTML) e a deduplicação (hash SHA-256 + embeddings pgvector) são processos independentes, não pipelines LLM. Os dois pipelines abaixo tratam exclusivamente do processamento por modelo de linguagem.
1
helpcore-analysis Consolidado

Executa 3 análises simultâneas por artigo em 1 única chamada LLM: classificação de inventário (14 campos), avaliação multidimensional de qualidade (10 campos) e análise intra-artigo de deduplicação (8 campos). A mesma entrada serve para as 3 análises, economizando 2/3 dos tokens de input.

Inventário — 14 campos
→ Qualidade — 10 campos
→ Dedup intra-artigo — 8 campos
→ 1 chamada LLM total
Output: 32 campos estruturados em 3 blocos (inventory, quality, dedup_analysis) por artigo • Provedor: OpenAI gpt-4.1-mini
2
helpcore-rewrite Sob Demanda

Reescreve artigos com overall_score de qualidade abaixo de 70 usando modelo de IA avançado. Ativado apenas para artigos que precisam de melhoria, economizando custo nos artigos de alta qualidade.

Filtro: quality overall_score < 70
→ Reescrita com Claude Sonnet 4
→ 12 campos de output
Output: Conteúdo reescrito + métricas delta de qualidade para ~5-10K artigos • Provedor: Anthropic Claude Sonnet 4

Detecção em 3 Camadas
1

Hash SHA-256

Normalização NFC + lowercase + whitespace collapse antes do hash. Identifica duplicatas exatas de forma determinística. Nenhuma chamada LLM envolvida.

NFC normalize lowercase whitespace collapse SHA-256 determinístico custo zero
~55K duplicatas esperadas
↓ apenas os ~52.7K únicos passam para a camada 2
2

Embeddings + pgvector

text-embedding-3-small (1536 dimensões). Índice HNSW (m=16, ef_construction=100) para busca KNN eficiente. Blocking via top-5 vizinhos evita comparação O(n²). Threshold ≥ 0.95 para merge automático; 0.92-0.95 vai para revisão humana.

text-embedding-3-small 1536d HNSW index cosine similarity ≥ 0.95 auto-merge 0.92-0.95 revisão humana
~3-5K duplicatas semânticas est.
↓ artigos não semânticos passam para fingerprint estrutural
3

SimHash / MinHash (Fingerprint Estrutural)

Detecta artigos com o mesmo conteúdo reorganizado ou reformatado de forma diferente. Complementar à similaridade semântica: captura casos onde a embedding não alcança threshold mas o conteúdo é substancialmente o mesmo.

SimHash 64-bit MinHash LSH Hamming distance ≤ 3 conteúdo reorganizado reformatação
~1-2K duplicatas estruturais est.

Pipeline de 4 Fases

Sequência de Execução Recomendada

Abordagem em 4 fases que garante eficiência máxima. Evita processar com LLM artigos que seriam descartados na fase de hash.

Fase 0

Normalização Pré-Ingestão

Normalização NFC + lowercase + whitespace collapse em todos os 108K artigos antes de qualquer inserção no banco. Geração dos hashes SHA-256.

Output: 108K hashes. Agrupamento de duplicatas exatas identificado. Apenas ~52.7K únicos avançam.
Fase 1

Ingestão dos Únicos

Apenas os ~52.7K artigos únicos são ingeridos com limpeza completa de HTML e extração de metadados. Duplicatas exatas recebem apenas flag e referência ao canônico.

Output: 52.7K artigos no PostgreSQL com metadados estruturados. 55.3K duplicatas registradas com referência.
Fase 2

Embeddings e Dedup Semântico

Geração de embeddings somente para os ~52.7K únicos via text-embedding-3-small. Construção do índice HNSW. Busca KNN top-5 para cada artigo. Merge automático ≥ 0.95.

Output: Índice pgvector construído. Duplicatas semânticas e estruturais identificadas e vinculadas.
Fase 3

Construção do Grafo

Materialização de todos os 6 tipos de vínculo na tabela article_relationships. Identificação de clusters temáticos. Construção de article_cluster_members com distância ao centróide.

Output: Grafo completo de relacionamentos. Clusters temáticos. Base pronta para classificação e quality score.

Riscos e Mitigações

Gestão de Riscos do Projeto

Cada risco identificado tem uma mitigação planejada. Nenhum risco é ignorado. Todos são gerenciados ativamente.

Dedup False-Positives Alta
Mitigação: Bug do PE corrigido e testado ANTES do pipeline. Validação com amostra de 1.000 artigos antes do full run.
Custo LLM excede orçamento Média
Mitigação: Dry-run de 100 artigos para extrapolar custo real. Heurísticas primeiro. LLM só para ambíguos (aproximadamente 10%).
Encoding de nomes de pasta Média
Mitigação: Detector automático de encoding (chardet). Fallback chain: UTF-8 → CP1252 → Latin-1. Log de conversões.
Artigos sem conteúdo processável Baixa
Mitigação: EMPTY_OR_ORPHAN (1.350) e MEDIA (288) catalogados com metadados mas sem score. Flag especial no schema.
Vazamento de conteúdo Baixa
Mitigação: Zero logging de conteúdo em plaintext. .gitignore para diretório de dados. Revisão de segurança antes do full run.
Performance do pgvector Baixa
Mitigação: Índice HNSW (m=16) já especificado. Benchmark com 10K artigos. IVFFlat como fallback se HNSW for lento.
