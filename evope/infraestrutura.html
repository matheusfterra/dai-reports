Process Studio Backend & Deploy

Documentação completa da infraestrutura server-side do Process Studio: API backend (NestJS), banco de dados (PostgreSQL/Prisma), deploy em Docker Swarm com HTTPS automático via Traefik, e pipeline CI/CD com GitHub Actions.

O backend do Process Studio é responsável por autenticação de usuários, sincronização de dados entre dispositivos, distribuição de atualizações do app desktop, e coleta de métricas de uso. O app desktop funciona 100% local mesmo sem conexão com o backend — a API é complementar, não essencial.

4Autenticação Implementado #

App (login)
→
POST /auth/login
→
JWT (15min) + Refresh (30d)
→
Device tracking
  • JWT Access Token: expira em 15 minutos (configurável via JWT_EXPIRATION)
  • Refresh Token: expira em 30 dias (configurável via JWT_REFRESH_EXPIRATION)
  • Refresh Token Rotation: a cada refresh, o token antigo é revogado e um novo é emitido
  • Device tracking: cada sessão é vinculada a um deviceId único
  • Senha: hash com bcrypt (salt rounds configurável)
  • Rate limiting: guard ativo em todos os endpoints de auth
  • Activity logging: toda ação de auth (login, logout, refresh, falha) é registrada com IP e user agent

5Sincronização de Dados Implementado #

O endpoint POST /sync/batch aceita até 50 itens por request. Cada item tem um tipo de entidade e um payload JSON:

Entity TypeDescriçãoCampos Principais
processProcesso gravado (trace)title, lifecycle, source_type, metadata
documentDocumento compiladodoc_type, step_count, word_count, content, file_url
metricEvento de telemetriaevent_type, payload, device_id, app_version
sessionSessão de usodevice_id, app_version, os_version, duration_ms
processing_errorErro de processamento do clienterror_type, phase, message, stack_trace, metadata

O sync é idempotente — itens com mesmo ID são atualizados (upsert). Documentos com mesmo file_hash são detectados como duplicatas. Validação de ownership garante que cada usuário só sincroniza seus próprios dados.

i

Local-first: o app funciona 100% offline. O sync é oportunista — envia dados quando há conexão, sem bloquear o uso.

5.1Gestão de Usuários Implementado #

Módulo admin para criar, listar, editar e desativar usuários. Todas as ações são registradas no log de auditoria automaticamente.

  • Criar usuário: POST /admin/users — email, nome, empresa, role (admin/user), senha
  • Listar: GET /admin/users — paginação, busca por nome/email, filtro por role e status
  • Editar: PATCH /admin/users/:id — alterar role, nome, empresa, ativar/desativar
  • Revogar sessões: DELETE /admin/users/:id/sessions — invalida todos os refresh tokens do usuário

5.2Erros e Monitoramento Implementado #

Sistema duplo de captura de erros: erros de processamento (enviados pelo client via sync) e erros do servidor (capturados automaticamente pelo exception filter).

Erros de Processamento (client-side)

  • Enviados via POST /sync/batch com entityType: "processing_error"
  • Rastreiam em qual fase o erro ocorreu (validação, geração, exportação, etc.)
  • Incluem stack trace, tipo de erro, versão do app e metadados
  • Consulta: GET /admin/errors e GET /admin/errors/summary

Erros do Servidor

  • Capturados automaticamente pelo HttpExceptionFilter global
  • Registram método HTTP, URL, status code, stack trace completo
  • Consulta: GET /admin/errors/server e GET /admin/errors/server/summary
!

Pendente no client: o backend já aceita processing_error no sync batch, mas o app desktop Tauri ainda não envia esses dados automaticamente. Essa integração está planejada.

6.2Migrations #

Migrations são gerenciadas pelo Prisma e aplicadas automaticamente no startup do container:

BASH
# Desenvolvimento - criar nova migration
npx prisma migrate dev --name descricao_da_mudanca

# Produção - aplicar migrations pendentes (roda no entrypoint do Docker)
npx prisma migrate deploy

# Gerar client após mudança no schema
npx prisma generate
!

O container roda prisma migrate deploy antes de iniciar a aplicação. Migrations destrutivas (drop column, drop table) devem ser feitas em duas etapas: primeiro remover o uso no código, depois a migration.

11Health Check Implementado #

Endpoint: GET /health (público, sem auth)

JSON - RESPOSTA
{
  "status": "ok",           // "ok" ou "degraded"
  "version": "0.4.25",
  "database": "connected",  // "connected" ou "disconnected"
  "uptime": 86400           // segundos
}

O Docker Swarm verifica o health a cada 30 segundos com timeout de 10s e 3 retries. Falha no health trigger rollback automático.

12Sistema de Auto-Update Implementado #

App Desktop
→
GET /updates/tauri/:target/:arch/:ver
→
Versão nova?
→
Download via API (proxy GitHub)
→
Instala automaticamente
  • O app verifica updates periodicamente usando o Tauri v2 updater nativo
  • A API funciona como proxy para o GitHub Releases (repo privado)
  • O download é servido via /updates/download/:ver/:file com token assinado HMAC-SHA256 com expiração
  • Admins publicam novas versões via POST /admin/versions
  • Cada check de update é registrado na tabela update_checks para analytics

Fluxo de Release

PASSOS
1. Build no Windows:  node release.cjs
   - Compila sidecar (.exe via pkg)
   - Compila app (Tauri + NSIS installer)
   - Publica no GitHub Releases

2. Registrar na API:  POST /admin/versions
   - version, target, arch, download_url, signature, release_notes

3. App detecta:  GET /updates/tauri/windows/x86_64/0.4.24
   - Retorna JSON com url + signature da nova versão

4. Download + instalação automática pelo updater Tauri
